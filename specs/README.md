# 规范中心

本目录是“访谈·体察 Agentic 系统”的规范单一入口，用于统一管理产品需求、架构、技术实现和 API 契约。规范文件使用稳定文件名，版本号写在文档内部，避免每次升级都造成链接失效。

公开仓库不分发维护者的生产发布脚本、交接单或真实验收资料。下文历史演进记录提到的内部路径仅作背景，不是开源安装前提；自建部署请以根目录 README 和 [`通用部署指南`](../examples/deployment/README.md) 为准。开源源码默认不会连接原项目站点或上报统计，统计必须由部署者主动配置。

## 2. 权威顺序

发生冲突时，按问题类型确定权威来源：

| 问题类型 | 权威文件 |
|---|---|
| 产品是否要做、范围和验收标准 | `PRD.md` |
| 系统边界、组件职责和部署限制 | `ARCHITECTURE.md` |
| 数据模型、并发、事务和实现方式 | `SPEC.md` |
| HTTP/SSE 请求响应契约 | `API.md` |
| 当前代码实际行为 | 源代码和自动化测试，仅代表实现现状 |

代码与规范不一致时，不允许直接把代码行为视为新需求。应先登记偏差，再决定更新规范、补齐实现或回退代码。

## 3. 文档依赖关系

```text
PRD.md
   ├─ ARCHITECTURE.md
   │      └─ SPEC.md
   └─────────┴─ API.md
                    │
                    ▼
              源代码与测试
```

- PRD 说明“为什么做、做什么”。
- Architecture 说明“系统如何划分、有哪些硬边界”。
- SPEC 说明“如何实现、如何保证正确性”。
- API 说明“模块之间如何交互”。
- 测试负责验证实现是否满足上述规范。

## 4. 文件与版本规则

### 4.1 文件命名

- 核心规范使用稳定的大写文件名：`PRD.md`、`SPEC.md`、`ARCHITECTURE.md`、`API.md`。
- 文件名不携带版本号；版本写入文件头部元数据。
- 新增独立模块规范时，使用子目录，例如 `specs/auth/PRD.md`，不要创建 `PRD_v2_final_new.md` 一类文件。
- 图片或图表统一放入 `specs/assets/`，使用相对路径引用。

### 4.2 版本号

规范版本采用 `主版本.次版本.修订号` 的语义：

- 主版本：产品范围、核心架构或兼容性发生破坏性变化；
- 次版本：新增能力、字段或接口，但保持已有能力兼容；
- 修订号：澄清文字、修正示例或补充不改变行为的说明。

API 与 SPEC 当前基线为 `v0.12`，产品 PRD 为 `v0.14`，其他文档以导航表为准。下一次仅做文字澄清可增加修订号；新增业务能力时升级次版本，发生破坏性变化时升级主版本。

### 4.3 文档状态

只使用以下状态：

- `草案`：内容可大幅调整，不能作为开发承诺；
- `评审中`：等待产品、研发或测试确认；
- `已评审`：作为当前基线；
- `实施中`：基线已明确，代码仍在补齐；
- `已实现`：自动化测试和实现均与规范一致；
- `已废弃`：保留历史说明，不再用于新开发。

## 5. 变更流程

### 5.1 新功能或范围变化

1. 先更新 `PRD.md`，写明目标、非目标、优先级和验收标准；
2. 若影响系统边界或部署方式，更新 `ARCHITECTURE.md`；
3. 更新 `SPEC.md` 的数据、状态、事务和异常设计；
4. 若影响接口，更新 `API.md`；
5. 再修改代码和测试；
6. 完成一致性检查后更新文档状态与版本。

### 5.2 缺陷修复

- 不改变对外行为：修复代码和测试即可，必要时在 SPEC 中补充实现约束；
- 改变接口、状态或错误语义：必须同步更新 `API.md`；
- 改变产品结果或验收口径：必须先更新 `PRD.md`。

### 5.3 紧急修复

紧急修复可以先恢复服务，但必须在同一开发周期内补齐规范，并在偏差登记中记录开始和关闭时间。

## 6. 更新检查表

每次调整规范或实现时检查：

- [ ] PRD 的范围、非目标和验收标准是否仍成立；
- [ ] 数据库字段、枚举、索引和迁移是否与 SPEC 一致；
- [ ] 实际路由、请求体、响应体和状态码是否与 API 一致；
- [ ] 单 Worker、进程内锁和 SSE 等架构限制是否仍成立；
- [ ] 新增配置是否同步到 `.env.example` 和 SPEC；
- [ ] 新增接口是否有成功、失败、幂等和并发测试；
- [ ] README、启动说明中的链接和命令是否仍有效；
- [ ] 文档版本、日期和状态是否更新；
- [ ] 是否存在未经确认的实现反向改变产品范围。

## 8. 评审与提交要求

- PRD 变更至少需要产品负责人确认；
- 架构、数据模型和迁移变更至少需要后端负责人确认；
- API 变更需要前后端共同确认，并同步测试用例；
- 规范变更应与对应实现位于同一提交或同一评审单中；
- 提交前只检查和提交已暂存内容，遵循仓库既有提交语言和确认流程；
- 不在规范中记录密钥、真实用户数据、服务器密码或其他敏感信息。
